# Mirsad First Working Version Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A runnable, locally verified Mirsad service: Telegram-shaped fixture intake, captures, AI review with officer handover, phone watchlist, reference dashboard and an HTTP contract another platform can integrate against.

**Architecture:** One TypeScript service (Hono + SQLite + local evidence directory). Intake, captures and review are separate stages joined by database rows and two in-process workers; every rule lives in the service and the dashboard is just another API client. Storage, rendering, inference, identity and channel adapters sit behind small ports.

**Tech Stack:** Node 24, TypeScript (strict, ESM, run with tsx), Hono, zod v4, SQLite, vitest, playwright-core against the installed Edge for dashboard e2e, LM Studio (OpenAI-compatible) for the local model. Exact versions: design section 19.

**Spec:** `docs/superpowers/specs/2026-11-21-mirsad-brief.md` (binding scope) and `docs/superpowers/specs/2026-11-21-mirsad-design.md` (decisions; sections are cited below as "design §N"). Executors read the design sections their task names.

## Global Constraints

- Bind to loopback only. The service refuses any other host.
- Credentials never enter the repository: `.env`, `data/` and `demo-credentials.json` stay git-ignored; `.env.example` holds names only.
- Message text, quotes, extracted values, phone numbers, display names and tokens never appear in logs or in stream event data.
- Original message text is never updated or deleted. Edits and deletions are separate events.
- Live Telegram content (`telegram_business_live`) is never sent to any model, including local inference. No code path sends a message to Telegram or WhatsApp.
- WhatsApp-specific implementation does not start in this plan. Intake refuses `source: 'whatsapp'` while the gate is closed (design §14).
- All data in fixtures, tests, examples and docs is synthetic. Domains end in `.test` or use `example.*`. Phone numbers come only from reserved fictional ranges: `+44 7700 900000`–`900999` and `+1 <area> 555 0100`–`0199`. Names are generic ("Test Contact", "Demo Officer 1").
- Exact UI and API strings: `New inbound`, `Dispatch`, `Contact started chat`, `Officer started chat`, `First observed: incoming`, `First observed: outgoing`, `Suspected fraud`, `Pause AI`, `Take over`, `Resume AI`, `Send`, `Leave unanswered`, `Message received.`, `Simulated send`, `Mirsad-rendered capture`, `Phone watchlist`, `Needs review`, `Watchlist match`, `No new finding`, `Ready for controlled test`, `Controlled test verified`.
- Every JSON response uses the envelope in design §5. Inaccessible chats answer exactly like missing ones (`404 chat_not_found`).
- Default model: Qwen3.5 9B Q4_K_M through LM Studio on a loopback URL with a 4,096-token context; URL and model ID are configurable. Tests use the deterministic reviewer or fakes, never the real model.
- TDD: write the failing test, run it and see it fail for the expected reason, then implement. Test output must be pristine (no warnings).
- Code style: files focused (aim under 300 lines, 800 ceiling), functions under 50 lines, no mutation of inputs in domain code, explicit error handling, no `console.log`, named constants for limits, zod validation at every boundary.
- Tests never sleep for a fixed time; they call `harness.drain()` or wait on a condition.
- Commit messages follow `<type>: <description>` (feat, fix, refactor, docs, test, chore).

## Review Focus

Inputs the brief implies but does not spell out; each has a named test in the owning task.

1. Hostile or malformed intake payloads (missing fields, unknown event type, oversized text, bad timestamps): rejected with `400`, nothing stored. → Task 2
2. Text that tries to spoof the record: markup, bidi overrides, control characters, very long messages: shown literally and never clipped silently. → Tasks 3 and 9
3. Two officers acting on the same chat at the same revision: exactly one wins, the other gets `409`. → Task 4
4. Restart in the middle of rendering or review: work resumes, no duplicate image or finding. → Tasks 3 and 6
5. A message longer than the model context, or a model that answers with invalid or instructed output: review degrades to unavailable or rejects unsupported items; capture is unaffected. → Tasks 6 and 8
